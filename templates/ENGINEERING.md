# ENGINEERING.md — инженерные правила проекта

> Нормативный документ: на него ссылаются скиллы, агенты-ревьюеры и скрипты-гейты workflow.
> Код нарушает правило — фиксируем нарушение, правило не ослабляем. Разделы, помеченные
> «заполнить», описывают ваш стек; остальное — общие правила процесса, их нумерацию не меняйте:
> на номера разделов ссылаются скиллы.

## 0. Уровень зрелости — объявить до кода

Перед реализацией определить уровень. Если не указан — спросить или считать **L1**.
Уровень пишется в `level:` техспека или в README сервиса.

- **L0 — прототип.** Проверить гипотезу. Один процесс, один файл, без очередей и алертов.
  Оверинжиниринг здесь — ошибка. `/prod-review` не применяется.
- **L1 — прод, текущий масштаб.** Сервис или агент + своя БД + внешние API. Обязательно всё из §2.
  Это default.
- **L2 — нагрузка / много писателей.** Реплики, распределённые локи, контейнеры, CI.
- **L3 — внешний SaaS.** Продукт для других организаций: изоляция арендаторов, tenant-aware
  авторизация и логи, SLO, лимиты и учёт потребления, нагрузочное тестирование, DR, экспорт и
  удаление данных арендатора, контрактная совместимость.

**Правило:** не применять решения уровня выше текущего. Считаешь, что нужен L2 — скажи текстом,
не тащи в код.

## 1a. Маршрут по размеру — `/build`

Не всякая правка идёт через конвейер спек. Размер процесса определяется **после короткой
разведки кода, а не до**. Команда `/build <что сделать>` делает разведку и применяет порог.

**Oneshot** (карточка на экран, код в той же сессии, одна ревью-линза, квитанция) — только если
выполнены **все** условия:

- ≤100 строк добавить или изменить;
- ≤5 файлов;
- нет записи наружу: запись в CRM или внешний API, сообщение клиенту, платёж;
- нет нового или изменённого юнита на сервере (процесс-менеджер, systemd, cron, контейнер);
- не меняется промпт или модель LLM-фичи в проде;
- уровень ≤ L1.

Одно условие не выполнено — полный конвейер: `/new-user-spec` (намерение не определено) или
`/new-tech-spec` (определено). Разведка не выбрасывается: `/build` сохраняет её черновиком
`code-research.md` в папке фичи. Сомнение трактуется в пользу полного конвейера; квитанция и
`owns-check` обязательны на обоих маршрутах. Тривиальная правка (опечатка, комментарий,
`.gitignore`) не требует и `/build`.

## 2. Обязательное — для любого сервиса и агента (Prod Gate, L1+)

Самопроверка перед запуском ревьюеров и перед коммитом. Читать только сработавшие блоки
`.claude/skills/prod-review/production-checklist.md`, не файл целиком.

- **Секреты только в переменных окружения / `.env`.** `.env` — в `.gitignore`. Не печатать
  секреты в лог и вывод.
- **Таймаут на каждый внешний вызов.** Без таймаута один зависший вызов вешает сервис.
- **Внешние API с лимитами** — уважать лимит провайдера, пакетные методы вместо цикла
  одиночных запросов, backoff при повторе.
- **Структурированное логирование.** Никаких `print()` в проде. Ошибка логируется с контекстом:
  сервис, идентификатор операции, время.
- **Graceful shutdown (SIGTERM)** для долгих операций — чтобы не рвать работу на полуслове.
- **Любая запись наружу идемпотентна.** Создание записи во внешней системе, сообщение клиенту,
  платёж — повтор запуска НЕ создаёт дубль. Natural key или таблица `processed_*` с уникальным
  ограничением; статус `pending → done` фиксируется в БД, не в памяти процесса (рестарт её
  обнуляет). Повтор **возвращает тот же идентификатор** (кэш ответа по ключу).
- **Ретраи — только идемпотентного и только на сетевые / 5xx / 429.** Не больше 3 попыток,
  экспоненциальная задержка с джиттером. Неидемпотентное при обрыве — помечать `unknown` и
  сверять, а не повторять вслепую.
- **Cron / фоновый цикл: лок от параллельного запуска** (файл-лок / `flock` / строка с TTL).
  Таймаут на итерацию; «мёртвые» элементы после N попыток помечаются и не блокируют очередь.
- **Вебхук: быстрый 200, обработка в фоне, дедуп по event id** — провайдеры доставляют повторно.
- **Списки — с лимитом.** Никаких `SELECT *` без `LIMIT` и запросов к БД в цикле (N+1).
- **Всё, что растёт, ограничивается в первой же версии.** Таблица, журнал, кэш: удаление старых
  данных, ротация по размеру, предел кэша.
- **Write-действие агента и деструктивная операция — только с подтверждением человека** или в
  заранее разрешённой узкой области (`DELETE`/`DROP`/массовый `UPDATE`, платёж, отправка клиенту).
- **Массовая операция имеет явный предел числа затронутых объектов.** Сначала посчитать, сколько
  затронем, потом сравнить с лимитом; превышение — отказ, а не выполнение «на всякий случай».
- **Вызов LLM логируется** с хешем промпта, версией модели, токенами и стоимостью. Автозапуск
  модели по расписанию закрыт гейтом (флаг + лимит стоимости на прогон и на сутки). Текст клиента
  и документы — данные, а не инструкции (тест на инъекцию); ПДн маскируются перед внешней моделью;
  изменение промпта прогоняется на eval-наборе.
- **На каждую фичу — ответ: «какая метрика покажет, что она сломалась, раньше пользователя?»**
  Латентность — в процентилях p50/p95/p99, не в среднем.

## 3. Веб-сервисы

- Валидация входа на каждом эндпоинте.
- `/health` → 200 обязателен.
- Авторизация на пользовательских роутах; rate limiting на публичных (429 с `Retry-After`).
- CORS — явный список origin, не wildcard в проде.

## 4. База данных

- Параметризованный SQL всегда; миграции — версионированными скриптами по порядку; перед
  изменением схемы — бэкап.
- Бэкап настроен и хотя бы раз проверен восстановлением.

## 4c. Готовность задачи — квитанция, а не слова

`status: done` у задачи ставится только по `work/<feature>/logs/receipts/task-N/acceptance.json`
с `accepted: true`, который пишет `python3 .claude/scripts/task-accept.py work/<feature> N`: скрипт
сам перезапускает команды верификации, проверяет, что исполнитель не вышел за `owns_paths` задачи
(`owns-check.py`), и что у ревьюеров нет `changes_required` и открытых critical-находок
(`findings-sync.py`). Перед запуском волны — `wave-check.py`: задачи одной волны не пересекаются ни
по записи, ни по «читаю то, что пишет сосед». Зелёный выход процесса, отчёт исполнителя и
«ревьюер согласился» основанием для `done` не являются. Квитанции лежат в `logs/receipts/` и едут
в git; `logs/working/` в `.gitignore`. Подробно — `.claude/scripts/README.md`.

## 4d. Возврат к старой фиче — сначала привести карточки к шаблону

Шаблон карточки задачи требует `owns_paths`, `reads`, `produces`, `authored_by` и неудаляемую
секцию TDD Anchor. На карточках без этих полей гейты деградируют молча: `owns-check` выходит с
кодом 3, `wave-check` пропускает задачу. Фича со старыми карточками **не запускается в работу,
пока её живые карточки (`planned` / `in_progress`) не приведены к шаблону**. `done`-карточки не
мигрируем.

**Общее правило:** ужесточение шаблона — это изменение над непустым корпусом. В том же изменении
называются три вещи: сколько существующих артефактов не соответствуют новой форме, что делаем с
уже закрытыми, и как ведут себя проверки на старой форме.

## 6. Коммиты и качество кода

- Semantic commits: `feat` / `fix` / `chore` / `refactor` / `docs`.
- Понятные имена (англ.), early return вместо вложенных if, комментарии только где логика
  неочевидна.

## 6.5. Формат завершения нетривиальной задачи

В конце каждой нетривиальной реализации — три строки, не больше:

```
Риски: <что сломается под нагрузкой или при частичном отказе внешнего API>
Отложено: <что осознанно не сделано и на каком уровне понадобится>
Наблюдаемость: <какая метрика / лог / алерт покажет поломку>
```

Если рисков нет — так и написать.

## 7. Когда вырастем (сознательно отложено, заполнить)

Не делаем сейчас — добавляем по факту необходимости, а не превентивно. Например: контейнеры на
каждый сервис, горизонтальный скейл, распределённый кэш, полный CI/CD, мультитенантность (L3).

## 8. Pre-Release Checklist

```
[ ] Секреты не в коде, .env в .gitignore
[ ] Таймауты на всех внешних вызовах
[ ] Логи через logger, ошибки с контекстом
[ ] Валидация входа и /health (веб-сервисы)
[ ] Бэкап БД настроен и хотя бы раз проверен восстановлением
[ ] Повторный запуск / повторный вебхук не создаёт дубль
[ ] Cron/воркер: лок от параллельного запуска, таймаут на итерацию
[ ] Есть метрика/алерт, который покажет поломку фичи
[ ] Рост ограничен: ротация логов, удаление старых данных, предел кэша
[ ] У каждого алерта есть условие, канал доставки и инструкция, что делать
[ ] LLM-фича: гейт автозапуска, лимит стоимости, прогон evals после изменения промпта
[ ] Блок «Риски / Отложено / Наблюдаемость» написан
```
