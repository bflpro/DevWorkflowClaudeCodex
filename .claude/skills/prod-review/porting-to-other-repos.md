# Как адаптировать продакшн-чеклист под свой репозиторий

Главное правило: **механика копируется, содержание адаптируется.** `production-checklist.md` написан
под конкретный стек (процесс-менеджер на VPS, SQLite, CRM и мессенджеры через REST, LLM API).
Оставить его как есть в репозитории с другим стеком — значит получать от модели советы под чужую
инфраструктуру: WAL для SQLite там, где Postgres, rate limit nginx там, где нет HTTP.

---

## Шаг 1. Механика — работает в любом репозитории без правок

- `.claude/scripts/reflex-check.mjs` — движок рефлексов (PreToolUse-хук), `.claude/reflexes/README.md`.
- `.claude/scripts/check-setup.sh` — диагностика, что хуки и скиллы подключены.
- Хук рефлексов в `.claude/settings.json`:

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Edit|Write|MultiEdit|NotebookEdit|Bash",
        "hooks": [
          { "type": "command",
            "command": "node \"${CLAUDE_PROJECT_DIR}/.claude/scripts/reflex-check.mjs\"",
            "timeout": 10 }
        ]
      }
    ]
  }
}
```

`${CLAUDE_PROJECT_DIR}` портативен; нужен установленный `node`. `.claude/settings.local.json`
(персональные права) — в `.gitignore`, в репозиторий не коммитится.

## Шаг 2. Инвентаризация стека — по коду, а не по памяти

Прочитать репозиторий и заполнить `ENGINEERING.md` §1 (стек) и §5 (деплой). Ответить на вопросы:

| Вопрос | Что от ответа зависит |
|---|---|
| Как запускается работа: HTTP-сервис, cron / systemd timer, процесс-менеджер, CI? | блоки A, D, H |
| Какая БД, сколько писателей? | блоки C, E |
| Какие внешние API пишут наружу (CRM, мессенджеры, платежи, git-push)? | блок B |
| Какие данные чувствительны (ПДн, медицинские, финансовые)? | блок G |
| Есть ли вызовы LLM? | блок J |
| Как выкатывается код и как откатывается? | блок H |

Главный риск репозитория бывает не там, где его ищет исходный чеклист. Пример: у репозитория без
HTTP-эндпоинта, который автоматически пушит конфиг и заметки в GitHub по крону, главный риск —
не «упадёт под нагрузкой», а «уедет наружу то, что не должно».

## Шаг 3. Адаптировать чеклист

1. **Буквы блоков A–J не менять** — на них ссылаются линза `prod-readiness`
   (`.claude/shared/review-lenses/prod-readiness.md`) и `ENGINEERING.md` §2.
2. Пункты, которых в стеке нет (WAL SQLite, nginx, pm2), — удалить или заменить аналогом
   (`systemd`-юнит вместо pm2, Alembic вместо ручных миграций).
3. Специфичный риск, которого нет в A–J, — **новый блок со своей буквой** после J
   (например, `S` — граница синка и секреты). Строку триггера добавить в таблицу шага 1 `SKILL.md`
   и в список блоков в `prod-readiness.md`.
4. Пункты про конкретных провайдеров (лимиты запросов, окна доставки сообщений) переписать под
   своих: точные лимиты и квоты, пакетные методы, ошибки, которые означают «уже принято».
5. Обновить таблицу триггеров в `SKILL.md` под реальные пути и библиотеки репозитория.

## Шаг 4. Рефлексы — только из реальных ожогов

Шесть рефлексов из поставки (`idempotent-external-writes`, `cron-parallel-lock`,
`mass-operation-limit`, `llm-scheduled-run`, `prod-review-before-deploy`, `runtime-data-not-in-git`)
общие, но их `use-when` написаны под исходный стек. Для каждого:

- переписать паттерны под свои команды и пути (имена клиентов API, деплой-скрипты, каталоги cron);
- проверить срабатывание на **реальной** команде из истории репозитория и молчание на заведомо
  безопасной — не на придуманной строке:

```bash
echo '{"tool_name":"Bash","session_id":"test-'$RANDOM'","tool_input":{"command":"<реальная команда>"}}' \
  | node .claude/scripts/reflex-check.mjs
```

  Ожидается JSON с `additionalContext`; пустой вывод — совпадения нет;
- рефлекс, который ни разу не сработал бы на реальной истории, удалить: новые заводить по факту ожога.

## Шаг 5. Проверка

1. `bash .claude/scripts/check-setup.sh` — ноль красных.
2. `/prod-review` на одном-двух самых рискованных файлах репозитория — первая живая проверка
   адаптированного чеклиста. Находки, которые оказались не про ваш стек, — сигнал вернуться к шагу 3.

## Чего не делать

- Копировать проектные скиллы в `~/.claude/skills/`: личная папка общая для всех репозиториев и
  перекрывает одноимённые проектные скиллы — правила одного проекта молча уедут в остальные.
- Ослаблять пункт чеклиста, потому что код ему не соответствует: фиксируется нарушение, а не правило.
