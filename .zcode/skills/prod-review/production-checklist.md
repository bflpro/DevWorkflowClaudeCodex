# Продакшн-чеклист по триггерам

Справочник. Не читается целиком — открывать только блок, чей триггер сработал (см. SKILL.md).
Исходный стек, под который писались пункты: сервисы и агенты на Python под процесс-менеджером
(pm2 / systemd) на VPS, SQLite/Postgres, CRM и мессенджеры через REST, LLM API. Пункты, завязанные
на этот стек, адаптируйте под свой — см. `porting-to-other-repos.md`. Ваш стек и деплой — `ENGINEERING.md`.

Уровни: **[L1]** — обязательно в проде, **[L2]** — только при реальной нагрузке / Postgres, **[?]** — обсудить.

## A. Триггер: роут, вебхук-хендлер, эндпоинт

- [L1] Pydantic-валидация входа; ограничение размера тела (`client_max_body_size` в nginx / лимит в коде)
- [L1] Вебхук от CRM / мессенджера / внешнего провайдера: быстрый 200, тяжёлая обработка — в фоне (task/queue), не в хендлере
- [L1] Вебхук может прийти дважды — дедуп по event id / хэшу тела за окно времени
- [L1] Проверка источника вебхука: секрет в URL или подпись; чужой запрос → 403, не обработка
- [L1] Rate limiting на nginx для публичных роутов (429 + Retry-After); внутренние вебхуки доверенных систем не лимитируем
- [L1] Авторизация: не только «залогинен», но «имеет право на этот объект» (сделка/дело/клиент)
- [L1] Таймаут на весь запрос; всё дольше ~2 с — в фон, ответ 202 + статус
- [L1] Списки — только с пагинацией и максимальным лимитом
- [L1] CORS — явный список origin
- [L1] Быстрый отказ при перегрузке: 503 сразу, а не ожидание до таймаута — медленный отказ копит очередь у вызывающего
- [L1] Изменение успешного ответа (поля, типы, порядок элементов) — ломающее: нужна новая версия эндпоинта, а не правка текущей
- [?] Версионирование при breaking change (`/v2/`), если у эндпоинта есть внешние потребители
- [L2] API-gateway / обратный прокси перед сервисом

## B. Триггер: побочный эффект наружу (запись в CRM, сообщение клиенту, платёж, внешний API)

- [L1] **Идемпотентность**: natural key или idempotency key + таблица/файл `processed_*` с уникальным ограничением.
  Повтор запуска НЕ создаёт вторую запись в CRM, НЕ шлёт второе сообщение клиенту, НЕ списывает дважды
- [L1] Порядок «сначала пометить как отправляемое → выполнить → пометить выполненным»; при падении между
  шагами статус `unknown` и сверка, а не слепой ретрай
- [L1] Таймаут + ограниченные ретраи (≤3) с экспоненциальной задержкой и джиттером; только на сетевые/5xx/429
- [L1] Ретраить только идемпотентное. Создание записи в CRM, отправка сообщения через провайдера — НЕ ретраить без ключа дедупа
- [L1] Есть `Retry-After` в ответе (429/503) — ждать столько, сколько сказал сервер, а не свой backoff: иначе продлеваем блокировку
- [L1] Идемпотентный ключ хранится вместе с SHA-256 тела запроса. Тот же ключ с другим телом → 409, а не молчаливая
  отдача старого результата (иначе «повтор» тихо возвращает ответ на другой запрос)
- [L1] **Ключ дедупликации неполон по построению, пока не перечислены все измерения**, различающие
  два законных действия: не только полезная нагрузка, но и адресат, канал и целевой объект.
  Один и тот же текст двум разным получателям — это два действия; ключ, собранный из одного тела,
  молча съест второе
- [L1] Защита от дубля ищет не по идентификаторам ТЕКУЩЕЙ записи (у дубля они другие по определению),
  а по устойчивому признаку намерения. Иначе слепнет ровно тогда, когда первая запись уехала
  дальше по процессу и сменила стадию/статус/id
- [L1] Маркер идемпотентности лежит в поле, которое **не может записать внешняя сторона**. Маркер
  в поле, доступном недоверенному источнику, — это решение об аутентификации, переодетое в вопрос
  формата
- [L1] Лимиты провайдера (запросов в секунду, квота на окно времени) соблюдаются в коде: пакетные методы
  (`batch`) для массовых операций вместо цикла одиночных запросов, пауза между страницами
- [L1] Ограничения канала доставки проверены до отправки: окно ответа мессенджера (вне окна — только
  одобренные шаблоны), лимиты на вложения и длину сообщения
- [L1] Состояние перехода хранится в БД/файле состояния, не в памяти процесса — рестарт процесса обнуляет память
- [L1] **Запись не затирает то, что появилось за время внешнего вызова.** Если запись состояния собрана
  до отправки/скачивания, а положена после, между этими точками успевает прийти вебхук: пишем
  полем/слиянием (`UPDATE ... SET col=?`, `patch`), а не целой записью, а флаги остановки защищаем
  в самом хранилище, а не в вызывающем коде. Типичный случай: стоп-флаг, поставленный вебхуком,
  через две секунды затирается записью той самой отправки, которая его и вызвала
- [L1] Логировать каждый шаг с `correlation_id` (deal_id / call_id / chat_id), без токенов и ПДн
- [L1] Массовая или деструктивная операция: посчитать число затрагиваемых объектов и сверить с явным лимитом;
  превышение → отказ с сообщением, а не выполнение (SRE Workbook, гл. 17)
- [L1] На границе с внешним сервисом сверяются счётчики отправленного и подтверждённого (сообщения, задачи,
  платежи); расхождение — алерт, а не строка в логе (Эволюционная архитектура, гл. 4)
- [?] Сверка (reconciliation): периодическая джоба сравнивает «что мы считаем отправленным» с реальностью
- [L1] Circuit breaker: после N ошибок подряд перестать долбить провайдера, алерт. Минимальная форма — счётчик
  подряд идущих ошибок в БД состояния + порог + пауза; библиотека не обязательна
- [?] LLM-вызовы: лимит токенов/стоимости на операцию и на сутки; модель и промпт версионированы

## C. Триггер: запрос к БД, новая таблица, отчёт

- [L1] Параметризованный SQL всегда
- [L1] Нет запросов в цикле (N+1) — батч / JOIN / `IN (...)`
- [L1] Индекс под каждый фильтр и сортировку; указать в миграции/DDL прямо в коде
- [L1] У каждой таблицы один владелец записи; остальные читают. Две точки записи в одну таблицу из разных
  процессов — это гонка, даже если сейчас «не совпадает по времени» (The Hard Parts, гл. 9)
- [L1] **Владение правилом о состоянии распространяется и на ЧИТАТЕЛЕЙ.** Выписать грепом по имени
  поля/таблицы всех, кто его читает, и сверить, одинаково ли они его интерпретируют. Два механизма,
  отвечающие на один вопрос о состоянии, расходятся молча; движок, доверяющий остаточным полям,
  которые UI прячет по флагу режима, и UI дают разные ответы об одной записи. Различие бывает
  намеренным — тогда его надо назвать и записать, а не оставить как совпадение
- [L1] Починка общего дефекта, сделанная у одного потребителя (пин версии, ручная правка во втором
  источнике, поле, дописанное мимо главного источника), невидима остальным и будет затёрта следующим
  автоматическим решением. Чинить в источнике либо явно перечислить, кто остался с дефектом
- [L1] `LIMIT` на любой список; `SELECT *` без лимита в проде запрещён
- [L1] SQLite: один писатель — `PRAGMA journal_mode=WAL`, `busy_timeout`; не держать транзакцию открытой во время сетевого вызова
- [L1] Конкурентная запись одной строки: `UPDATE ... WHERE version = ?` либо транзакция `BEGIN IMMEDIATE`
- [L1] Механизм защиты конкурентной записи **объявлен явно**: атомарная операция, `BEGIN IMMEDIATE` или
  compare-and-set по версии. Read-modify-write без одного из них — это потерянное обновление
- [L1] Транзакция, упавшая на блокировке (`database is locked` / deadlock), повторяется — в отличие от прочих ошибок записи
- [L1] При записи инвалидируются производные данные: кэши, снапшоты, поисковые индексы. Синхронизация —
  обязанность кода приложения, БД её не сделает
- [L1] Не грузить неограниченные наборы в память — итерировать курсором / батчами
- [?] Если нужна многопользовательская конкурентная запись — это сигнал к Postgres, а не к костылям в SQLite
- [L2] Реплики чтения, партиционирование — только с Postgres и доказанной нагрузкой

## D. Триггер: cron-агент, процесс под процесс-менеджером (pm2 / systemd), фоновый цикл

- [L1] Обработчик идемпотентен — событие/строка может прийти дважды (см. B)
- [L1] **Лок от параллельного запуска** (файл-лок / `flock` / строка в БД с TTL); прошлый запуск мог не завершиться
- [L1] **Отказ без следа переодевается в чужую неисправность.** Выход по таймауту блокировки,
  по закрытому предохранителю и по любому «мы решили не работать» пишет ОТЛИЧИМУЮ строку с причиной
  и двигает свой счётчик. Молчаливый выход превращает медленный обработчик в «функция не работает»,
  и расследование уходит в логику, которая исправна
- [L1] Сигнал, который узнаётся асинхронно (ответ вебхука, готовность файла, снятие лока), имеет
  СВОЙ путь пробуждения обработчика. Реакция, висящая на тике соседнего шага, работает по везению
- [L1] Импортированный, но ни разу не вызванный защитный механизм — это его отсутствие: греп имени
  функции по ВЫЗОВАМ, а не по импортам. Такой механизм невидим для всех проверок сразу
- [L1] Таймаут на выполнение одной итерации / одной задачи — иначе воркер виснет навсегда
- [L1] Ограниченное число попыток на элемент + «мёртвые» элементы помечаются и не блокируют очередь (DLQ = таблица/файл `failed_*`)
- [L1] Задача принимает id, а не сериализованный объект — объект успеет протухнуть
- [L1] Долгая операция: её идентификатор сохранён на диск/в БД до начала опроса — рестарт процесса не теряет наблюдение
  за уже запущенной работой
- [L1] Синтетические и тестовые записи в проде помечены флагом и отфильтрованы из метрик и из восстановительных
  циклов. Непомеченная тестовая запись живёт в проде годами
- [L1] Graceful shutdown по SIGTERM: дообработать текущий элемент, зафиксировать состояние — но не дольше таймаута
- [L1] Порядок старта: ресурсы (БД, пул соединений, внешние клиенты) инициализированы до приёма работы;
  недоступна БД — процесс не стартует, а не принимает запросы и падает на первом
- [L1] **Политика перезапуска выбрана осознанно под характер работы.** Процесс с КОНЕЧНОЙ работой
  (разовый скрипт, миграция, обход очереди «до опустошения») под `autorestart` превращается в цикл —
  и в цикл уведомлений вместе с ним: ему `autorestart: false` / `--no-autorestart` / oneshot-юнит
  с таймером. Уведомления такого процесса подчиняются идемпотентности блока B: рестарт не порождает
  второе сообщение
- [L1] У долгоживущей службы, наоборот, есть ВТОРАЯ попытка старта: `max_restarts`/`restart_delay`
  заданы, при краше нет бесконечного рестарт-лупа без алерта, а перезапуск, инициированный снаружи
  (автообновление пакетов, ребут хоста), не оставляет её лежать до утра
- [L1] Метрика: длина очереди / возраст самого старого необработанного элемента / время последнего успешного прогона → push в uptime-монитор или панель дашборда. Алерт на рост
- [L1] **Возраст самого старого необработанного элемента измеряется обязательно**, и выборка
  исполнителя не у́же выборки планировщика. Строка, которую планировщик видит, исполнитель не берёт,
  а срок годности ей не задан, — бессмертная строка очереди: её не исполнит и не уберёт никто
- [?] Backpressure: если входящих больше, чем обрабатываем — ограничить приём, а не копить бесконечно
- [?] Приоритеты: длинные задачи не блокируют короткие

## E. Триггер: изменение схемы БД, миграция

- [L1] Бэкап файла `.db` перед миграцией; откат описан
- [L1] Миграции — версионированные скрипты по порядку, применяются идемпотентно (повтор не ломает)
- [L1] Миграция применяется шагом деплоя, а не руками по ssh: ручной шаг рано или поздно пропустят
  (Эволюционная архитектура, гл. 6)
- [L1] Совместимость вперёд: сначала добавить колонку/таблицу, задеплоить, потом удалять старое
- [L1] Бэкфилл больших данных — батчами в фоне, не внутри миграции
- [L1] **Расширение ключа дедупликации или уникального индекса на работающей системе — это миграция,
  а не правка кода.** Уже обработанные строки посчитаны по СТАРОМУ ключу, поэтому порядок такой:
  пишем оба ключа → бэкфиллим новый по историческим строкам → переключаем чтение → только потом
  снимаем старый. Иначе первый же прогон после выкладки считает всю историю необработанной
  и шлёт её заново
- [L2] Postgres: Alembic; индексы `CONCURRENTLY`; `NOT NULL` через промежуточный шаг

## F. Триггер: Telegram-бот, long-polling, реалтайм

- [L1] Переподключение с backoff при обрыве polling / websocket
- [L1] Обновления Telegram могут прийти повторно после рестарта — дедуп по `update_id`
- [L1] Состояние диалога — в БД/файле, не в памяти процесса
- [L1] Лимит на пользователя (частота сообщений, размер вложений)
- [L1] Переход на человека доступен с любого узла диалога и протестирован на первых узлах
- [L1] При низкой уверенности не действовать: переспросить, подтвердить намерение, при повторном непонимании —
  эскалация. Без обвинения пользователя (Conversational AI, гл. 4)
- [L1] Тестируется каждая ветка сценария и каждое правило, а не только happy path
- [L1] Heartbeat: монитор uptime на «бот жив» (push с интервалом), а не только на наличие процесса
- [?] Выбор транспорта: polling — default; webhook — когда нужна низкая задержка и есть публичный HTTPS

## G. Триггер: безопасность, auth, секреты, ПДн

- [L1] Секреты только в `.env` / env; `.env` в `.gitignore`; ротация без пересборки
- [L1] В логи не попадают токены, ключи, ПДн клиентов (ФИО+паспорт, телефон, ИНН)
- [L1] JWT: проверка подписи и `exp`; короткий access
- [L1] Параметризованный SQL; экранирование вывода в HTML
- [L1] SSRF: URL от пользователя — по allow-list, приватные IP запрещены
- [L1] Персональные данные клиентов (документы, паспортные данные) — шифрование на диске или доступ только по ролям; никаких копий между проектами
- [L1] ПДн не уходят во внешние модели: маскирование плейсхолдерами перед отправкой и обратный словарь на ответ;
  запрос, требующий извлечения ПДн, блокируется фильтром
- [L1] Сервисные учётки с минимальными правами: доступ к чужой БД — readonly, вебхуки и токены — только с нужными scope
- [L1] При неопределённости security-критичная операция завершается отказом (fail closed). Выбор fail-open
  допустим только осознанно и записан в решении (BSRS, гл. 8)
- [L1] Никакой самописной криптографии и самодельных подписей — только проверенная библиотека
- [?] Аварийный доступ (breakglass) поднимает алерт и попадает в аудит
- [?] WAF / защита периметра — на уровне провайдера
- Глубокий аудит — `security-auditor` (Opus), не здесь

## H. Триггер: деплой, nginx, процесс-менеджер, бэкап

- [L1] Код выложен в runtime-каталог сервиса **до** рестарта процесса (`pm2 restart` / `systemctl restart`), а не после
- [L1] `nginx -t` перед reload
- [L1] `/health` → 200 для web-сервисов; readiness (с БД) отдельно от liveness, если есть
- [L1] Откат описан: предыдущая версия кода доступна, бэкап БД есть
- [L1] Бэкап **проверен восстановлением** хотя бы раз. Непроверенный бэкап — не бэкап
- [L1] Перед применением бэкапа проверяется контрольная сумма или подпись: повреждённый архив хуже отсутствия
  бэкапа, потому что создаёт ложную уверенность (BSRS, гл. 9)
- [L1] Зависимости зафиксированы (`requirements.txt` с версиями / lock)
- [L1] Ротация всех журналов по размеру с лимитом числа файлов (`RotatingFileHandler` / logrotate / pm2-logrotate)
- [L1] `ruff` + `black` (+ тесты) прошли

**Приёмка самого шага выкладки** (правило не про конкретный инструмент — годится для `rsync`, `cp`,
`scp`, пайплайна CI):

- [L1] У каждого шага проверяется **код возврата**, а не наличие вывода. Шаг, обёрнутый в подсчёт
  строк или уехавший в пайп, отдаёт код последней команды: отказ выглядит как «скопировано ноль
  файлов», а не как ошибка. `set -euo pipefail`, либо явная проверка кода нужной команды
- [L1] **Нулевой код возврата — не вердикт.** После шага утверждается ОЖИДАЕМОЕ состояние: файл на
  месте, контрольная сумма совпала с источником, процесс поднялся с новой версией. Сверка идёт
  ДО рестарта: проверка после рестарта уже не может его отменить
- [L1] Выкладка синхронизацией каталога выкатывает не правку, а весь накопившийся отрыв. **Сухой
  прогон обязателен** (`rsync --dry-run`, `diff -r`), а его вывод — часть квитанции, а не разовый
  взгляд глазами
- [L1] Не выкладывать через ОБЩИЙ временный каталог: чужой файл с тем же именем уедет в прод, а отказ
  записи не остановит шаг. Распаковка и сборка — в каталог, уникальный для прогона
- [L1] Команда проверки пишется в том виде, в каком её прочтёт САМЫЙ ШИРОКИЙ будущий читатель
  (квитанция в git, чужой прогон, CI): явные пути, без интерактивных флагов, без зависимости от cwd,
  алиасов и текущего окружения
- [L1] Изменение шелла или окружения сервисной учётки проверяется ПРОТИВ ограничителей, которые на ней
  висят (forced command, restricted shell, `command=` в `authorized_keys`): негативная проверка
  безопасности выполняется ПОСЛЕ изменения и от лица той же учётки, иначе она зелёная по инерции
- [?] Feature flag для рискованных изменений (env-переключатель)
- [L2] Docker, CI-pipeline, автоскейл, IaC — см. ENGINEERING.md §7

## I. Триггер: любая новая заметная фича (всегда)

- [L1] Ответ на вопрос: **«какая метрика/лог покажет, что фича сломалась, раньше пользователя?»** Если ответа нет — добавить push в uptime-монитор / панель дашборда / алерт
- [L1] Структурированные логи с `service` + идентификатором операции, прокинутым насквозь
- [L1] Ошибки — в Sentry/лог с контекстом; пустой `except: pass` запрещён
- [L1] Алерт на симптом для пользователя (нет прогонов за N часов, рост ошибок), а не на CPU
- [L1] У каждого алерта есть условие, канал доставки и инструкция, что делать. Алерт без инструкции
  превращается в шум за две недели (DMLS, гл. 8)
- [?] Есть SLO — алертить на скорость расхода бюджета ошибок, а не на мгновенное превышение порога
  (SRE Workbook, гл. 5)
- [L1] Состояние точек интеграции наблюдаемо: число ошибок подряд, состояние предохранителя, время последнего успеха
- [L1] Время ответа измеряется на стороне вызывающего и в процентилях p50/p95/p99 — среднее на сервере скрывает
  блокировку очереди
- [?] SLO — когда есть обязательство перед клиентом

### Приёмка индикатора (плитки, счётчика, алерта) — от точки ЗАПИСИ, а не от вида на экране

Индикатор принимается не по тому, что он отрисовался, а по тому, кто и когда двигает число.

- [L1] Названа **точка записи**: какой код инкрементирует/пишет это число, и перечислены ли ВСЕ ветки
  отказа, которые обязаны его тронуть. Счётчик, который никто не увеличивает, зелёный всегда; правило
  деградации без своего счётчика — декорация. Путь обнаружения, описанный в рунбуке, но не имеющий
  кода, который его кормит, — то же самое
- [L1] Признак «это наш инцидент» не построен на факте существования строки, которую создаёт
  ПОСТОРОННИЙ контур, и исходящее сообщение не лежит в том же журнале, по которому меряют его эффект
- [L1] Названа **одна строка данных** (запрос с ожидаемым результатом), подтверждающая крайнее значение:
  и пустоту, и максимум. Новый фильтр над списком из конфига ломается в сторону пустоты, а пустой
  экран наблюдения читается как «проблем нет»
- [L1] Сказано, **куда поедет метрика, когда система встанет**: сломанная фича обязана двигать число
  в сторону тревоги, а не обнулять его и не украшать. Плитка «запланировано на ближайшие N часов»,
  посчитанная как `due <= now + N`, тем бодрее, чем хуже дела: застрявший бэклог выглядит как план
- [L1] Есть утверждение о **непустоте** (строк больше нуля) и о **моменте перехода**: статус,
  переписываемый на месте без `*_at`, превращает любой разбор инцидента в догадку — и выясняется это
  в день разбора. Новый путь доступа к ресурсу сверяется со старыми метриками обращений к нему:
  молча обесцененная метрика неотличима от спокойствия

## J. Триггер: вызов LLM в коде (промпт, агент, цепочка, судья)

Срабатывает, когда в диффе есть обращение к модели (`openai`, `anthropic`, `deepseek`, `httpx` к API
провайдера), файл промптов, агентная цепочка или оценка качества ответов.

- [L1] Текст от клиента и содержимое документов **не исполняются как инструкции**. Есть тест: подложить
  в читаемый источник «IGNORE PREVIOUS INSTRUCTIONS AND ...» и убедиться, что поведение не изменилось
- [L1] Guardrails стоят и на входе, и на выходе модели. Фильтр только на входе не ловит утечку в ответе
- [L1] Автозапуск модели по расписанию закрыт гейтом: флаг включения + лимит стоимости на прогон и на сутки.
  Негейтованный ночной прогон по cron замечают только постфактум — по счёту
- [L1] Модель не обещает клиенту того, что исполняет СЛЕДУЮЩИЙ этап. Если вход того этапа не распознан,
  обещание уже дано, а исполнения не будет: всё обещанное в тексте ответа либо уже исполнено, либо
  имеет проверенный путь исполнения с известным условием распознавания
- [L1] Ответ модели проверяется на ожидаемый формат (валидный JSON, допустимые значения); иначе retry
  или fallback на другую модель, а не падение и не «как есть» дальше по коду
- [L1] Запросы с ПДн и запросы, зависящие от текущего времени, не кэшируются
- [L1] Промпт считается публичным артефактом: секретов и ПДн в system prompt нет (LLMs in Production, гл. 7)
- [L1] Мониторится качество отдельно от доступности: дрейф входных текстов, доля отказов модели
  (refusal rate), распределение решений. Падение качества не видно по кодам ответов (DMLS, гл. 8)
- [L1] Изменение промпта прогоняется на eval-наборе и сравнивается с baseline; промпт версионируется
  отдельно от кода, в логах — его хеш
- [?] Model Gateway: вызовы провайдеров идут через одну точку с fallback, а не прямыми обращениями к SDK по всему коду
- [?] AI-судья как метрика: температура 0, рубрика, фиксированная версия промпта рядом с результатами;
  один судья не является основанием — рядом должна быть детерминированная проверка или человек

## Общие ловушки

- Глобальный изменяемый стейт в async-коде — гонки
- Незакрытые соединения / клиенты, растущие кэши и списки без ограничения — утечки
- Сравнение времени с разных машин — не делать; для порядка событий — счётчики/версии
- Зависимости без версий — «работало вчера»
- Регулярный перезапуск по расписанию как лечение утечки или гонки — маскировка дефекта, а не решение
- `ERROR` в логе на ошибку пользовательского ввода — дежурный перестаёт читать ERROR; для этого `WARNING`
- Строка журнала, написанная на длящееся СОСТОЯНИЕ («режим выключен», «канал недоступен»), а не на
  переход в него: её объём равен частоте вызывающего, и та же частота задаёт нужный ключ троттлинга.
  Логировать переход, текущее состояние отдавать метрикой
