# Prod Review

Цель: найти то, что сломается не сегодня, а на сотне запусков, при частичном отказе
внешнего сервиса или при повторной доставке события. Дополняет `/review` (логика, читаемость)
и `security-auditor` (OWASP) — не дублирует их.

## Шаг 1. Область и уровень

1. Собрать дифф: `git diff main...HEAD` или указанные файлы/папку агента.
2. Определить уровень зрелости (из tech-spec `level:`, из README агента или спросить).
   L0 → сказать «прототип, prod-review не применяется» и остановиться.
3. Определить сработавшие триггеры по диффу:

| Что в диффе | Блок в `production-checklist.md` |
|---|---|
| роут, вебхук-хендлер, эндпоинт FastAPI/aiohttp | A |
| запись в CRM (задача/сделка/лид/комментарий), отправка сообщения клиенту (мессенджер/SMS/email), платёж, любой внешний вызов с побочным эффектом | B |
| SQL, схема SQLite, новый отчёт/выборка | C |
| cron-агент, процесс под pm2/systemd, фоновый цикл, очередь | D |
| изменение схемы БД / миграция | E |
| Telegram-бот, long-polling, websocket | F |
| auth, токен, `.env`, персональные данные клиентов | G |
| деплой на VPS, nginx, конфиг процесс-менеджера (pm2 ecosystem / systemd unit), скрипт бэкапа | H |
| новая заметная фича (всегда) | I |
| вызов LLM: `openai`/`anthropic`/`deepseek`, файл промптов, агентная цепочка, оценка ответов | J |

Читать **только** сработавшие блоки чеклиста. Не читать файл целиком.

4. Разобрать, что во входных данных ревью — **факт**, а что — догадка о его охвате. Если в задании
   есть «уже установленный факт», числа из прошлой диагностики или указание «самое опасное место —
   вот здесь, механизм такой-то»:
   - факт берём, его **охват считаем неизмеренным**: охват выведен из механизма, который имел в виду
     автор задания, и потому систематически занижен — переснимаем сами;
   - числа, унаследованные от предыдущей диагностики, наследуют и **момент съёма**. Пересняли —
     пишем свои; не пересняли — помечаем «со слов, не перепроверено»;
   - чистый результат ИМЕННО в названном месте закрывает только те ветки механизма, которые мы
     реально прошли. В отчёте так и писать: «чисто по веткам A и B», а не «место чисто».

## Шаг 2. Проверить

По каждому пункту сработавшего блока — один из трёх вердиктов:

- **есть** — реализовано, указать `файл:строка`
- **нет** — не реализовано, требуется
- **не нужно** — одна строка обоснования

Пункты `[L2]` проверять только если объявлен уровень L2.

## Шаг 3. Автопроверки

Прогнать по диффу, результат приложить одной строкой:

```bash
# линтер / тесты, если есть в проекте
ruff check <files>; pytest -q 2>/dev/null
# ловушки
grep -nE "except\s*:|except Exception\s*:\s*$" <files>          # пустой except
grep -nE "requests\.(get|post|put|delete)\(" <files> | grep -v timeout   # без таймаута
grep -nE "httpx\.(get|post|AsyncClient)\(" <files> | grep -v timeout
grep -nE "time\.sleep\(" <files>                                  # sleep в хендлере
grep -nE "SELECT \*" <files>
grep -nE "(openai|anthropic|genai|deepseek)\." <files> | grep -v gateway   # прямой вызов SDK мимо шлюза
grep -nE "(httpx|requests)\.(get|post)" <files> | grep -vE "timeout|Timeout" # внешний вызов без таймаута
grep -nEi "ignore previous|prompt.?injection" tests/ 2>/dev/null            # есть ли тест на инъекцию
grep -rnE "logger\.(error|exception)" <files> | head                        # ERROR только на то, что требует действий
grep -nE "(api_key|token|secret|password)\s*=\s*['\"]" <files>    # захардкоженный секрет
grep -nE "print\(" <files>                                        # print вместо logger
grep -n "TODO\|FIXME" <files>
```

## Шаг 4. Отчёт

Формат строго такой:

```
## Блокеры (не деплоить)
1. <проблема> — <файл:строка> — <как чинить, 1 строка>

## Стоит поправить
1. ...

## Отложено осознанно
1. <пункт> — <почему можно жить без него на текущем уровне>

## Наблюдаемость
Какая метрика/алерт/лог покажет поломку раньше пользователя. Если нет — что добавить (push в uptime-монитор / панель дашборда / лог с id).

Автопроверки: <одной строкой>
```

Правила отчёта:

- В блокеры — только потеря данных, двойное действие с побочным эффектом (дубль-запись в CRM,
  двойное сообщение клиенту, двойное списание), дыра в безопасности/ПДн, полная недоступность.
  Остальное — во второй раздел.
- Не больше 7 пунктов суммарно в первых двух разделах. Больше — выбрать самое дорогое,
  остальное свернуть в одну строку.
- Пустой раздел — писать «пусто», не выдумывать замечания ради объёма.
- Код не переписывать. Патч показывать только для блокеров.
